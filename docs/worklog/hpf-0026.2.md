## What was built

1. **Loader and validator** (scope 1).
   - `loadPrereqGraph()` fetches `/frameworks/framework_prereqs.json`, memoised
     like `loadFramework`. A 404 returns null.
   - `validatePrereqGraph(raw, knownIds)` (`prereqs.ts:73`) rejects:
     - a payload without an `edges` array, and edges without string `from`/`to`
     - unknown ids
     - self-loops
     - duplicate from/to pairs, whatever their strengths
     - a strength other than `hard`/`soft`
     - cycles over hard and soft edges together (DFS, `:111`); the error names
       the closed path
   - `prereqGraphOrNull` (`:157`) is the runtime entry point. A missing,
     unreadable or invalid graph returns null and logs a `console.warn`
     containing "fail open". A null graph gates nothing.
2. **Taught** (scope 2). `taughtEntryIds(rows, reads)` (`:182`): a
   `framework_progress` status of learning, practicing, retaining or
   mastered, or membership in the merged lesson-read set. Untaught rows,
   unknown statuses and missing rows read as untaught. The newest row per id
   wins, as in `summarizeFrameworkProgress`.
   - `useDailyPlan` now calls `useFrameworkProgress()`.
   - Hint resolution waits while that query `isLoading`, the same "settled"
     test the hook already applies to the server plan. `hints` stays null, so
     the plan is not generated and `isLoading` stays true.
   - An errored or paused query counts as settled with no rows, so the gate
     runs on the read set alone.
3. **Hard edges, introduction only; pull-forward; soft order** (scopes 3–5),
   in `pickLessonEntry` (`:226`). For each section:
   1. Candidates are the unread entries. Soft-satisfied entries (every soft
      prerequisite taught) come first; each group keeps catalog order.
   2. The first candidate is introduced unless it is blocked: still untaught
      and with an untaught hard prerequisite. An entry past `untaught` is
      never blocked.
   3. A blocked candidate pulls forward its deepest untaught hard
      prerequisite. At each step the walk follows the first untaught
      prerequisite in file order, down to one whose own hard prerequisites are
      all taught.
   4. If that prerequisite cannot be shown (its catalog did not load), the
      next unblocked candidate is introduced. If there is none, the hint is
      `null`, which skips the lesson as an all-read section does.
   - `resolveFrameworkHints` (`useDailyPlan.ts:591`) builds an id index over
     every loaded catalog. A pulled-forward hint therefore carries the
     prerequisite's own section and headword:
     `{ id, headword, pulledForward: { section, blockedId } }`.
   - `lessonItem` uses the prerequisite's section for `section`, `id`, `href`
     (`/lektion?section=<prereq section>#<prereq id>`) and headline. The
     rationale is `Grunden först: läs <A>-regeln som den här <B>-fällan
     bygger på.`, where B is the lesson slot's own section.

## Decisions (my calls where the spec left room)

- **Which entry is "the candidate".** The candidate is the first entry after
  the soft ordering, whether or not it is blocked. Choosing only among
  unblocked entries would make pull-forward unreachable. The proposal's
  "filtered by hard eligibility" wording therefore governs the fallback list.
  On shipped data this is the plain first unread entry, as before.
- **Unknown ids while a catalog is missing.** With every catalog loaded, the
  runtime validates ids against all of them. If one catalog failed to load,
  its ids cannot be told apart from a typo. In that case only the unknown-id
  check is deferred (`knownIds = null`) and every structural check still
  runs. Without the deferral, one failed XYZ load would fail the whole graph
  open. Scope 4's "prerequisite cannot be resolved, fall back" path would
  then be unreachable.
  - Worst case: a typo'd prerequisite during that degraded load reorders a
    section's lessons. It never blocks learning.
  - The build-time test validates the shipped graph against both catalog
    copies.
- **Per-section load errors are now caught.** At 89adad9, one framework HTTP
  error rejected `resolveFrameworkHints` with no catch. `hints` then stayed
  null and Home never left loading. Now that section is left out of the hints,
  and a prerequisite in it falls back as scope 4 says. This behaviour change
  was needed for the fallback.
- **The pulled-forward lesson still fills the slot.** The weakest section
  counts as having its lesson that day, so Rule 2b gives it no extra drill
  (scope 4: "the lesson slot becomes…").
- **Several hard prerequisites.** The first untaught one in file order wins
  at each step, which keeps the walk deterministic. No shipped entry has two.
- **Warnings are not deduplicated.** Each hint resolution warns again,
  about 2–3 times per Home mount, for a graph that the test suite already
  guards.
